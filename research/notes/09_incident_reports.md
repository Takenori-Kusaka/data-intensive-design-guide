## 1. 問い（このノートが答えること。対応する Part）

- 大規模サービスを長時間止めた事故は、事業者自身の報告によれば、何が引き金で、どの設計・取り決めの欠陥が被害を広げたのか
- それらは少数の「型」にまとめられるか。型ごとに事業者が挙げた対策に共通点はあるか
- 「設定・ルール・メタデータもデータであり、コードと同じく段階配布と互換性検査が要る」と言える根拠はあるか
- 設計レビューで、型ごとに何を問えばよいか
- 対応する Part：14（共通基盤）、15（正しさと障害）、および各 Part の「事故の例」

### 4.3 分析 1：原因の型

1 件が複数の型に入る。「引き金」と「被害を広げた欠陥」を分けて見ると、引き金はばらばらでも、広げた欠陥は少数の型に集まる。

- 19 件のうち、引き金が「ハードウェアや電源の故障」だったのは Cloudflare 2023・2020、GitHub 2018 の 3 件。残りは変更（コマンド、設定、更新、容量追加、展開）が引き金だった
- 長引いた件（Roblox 73 時間、Atlassian 最長 14 日、Datadog 約 48 時間、Cloudflare 2023 約 41 時間、GitHub 2018 約 24 時間）は、いずれも「空の状態から戻す」「大量に戻す」手順を事前に試していなかったと報告が述べている
- 「安全のための仕組み」が被害を広げた件が多い：検証器（CrowdStrike）、設定の自動修正（Facebook 2010）、失敗時に全部通す安全装置（Cloudflare 2024）、自動昇格（GitHub 2018、Cloudflare 2020）、ヘルスチェック（AWS 2025、Azure 2026）、自己取り下げ（Facebook 2021）、停止スイッチ（Cloudflare 2025-12）

### 4.4 分析 2：「設定やルールもデータであり、段階配布と互換性検査が要る」の根拠

| 件 | 配られたもの | コードと同じ扱いを受けていなかった点 | 事業者自身の言葉・対策 |
|---|---|---|---|
| CrowdStrike 2024 [12] | 検知ルール（Channel File） | センサー本体は試験と認証を通るが、ルールは検証器だけで全体に配布。項目数の取り決め（21 対 20）を誰も照合していない | 「設定データであり、コードではない」と位置づけたうえで、ルールにも段階配布・カナリア・顧客側の制御を入れた |
| Google Cloud 2025 [13] | 割当ポリシー（Spanner の行） | バイナリはリージョンごとに配ったが、その経路を踏むポリシーは数秒で全世界に複製 | 全世界に複製するデータは段階的に流して検証する、と明記 |
| Cloudflare 2025-11 [14] | 自社で生成する特徴量ファイル | 5 分ごとに全体へ。大きさも重複も検査せず、読む側は上限超えで落ちる | 自社生成の設定を利用者入力と同等に検査する、と明記 |
| Cloudflare 2025-12 [22]・行動計画 [24] | WAF の設定 | 同じ作業の中で、片方は段階配布、片方は数秒で全体。報告自身が対比している | 設定変更にもソフトウェアと同じ段階配布を義務づける（Code Orange: Fail Small） |
| Cloudflare 2024-11 [15] | ログ転送の設定 | 空の設定が正しい値として配られ、読む側は「全部送る」と解釈 | 過負荷試験と設定漏れの警報 |
| Google 2020 [20] | 割当の値 | 新旧の仕組みの食い違いから出た「0」が、自動で全世界に効いた | 割当の自動化が全世界に速く効かないようにする |
| Cloudflare 2026-02 [23] | API のフラグ | 値なしのフラグを、呼ぶ側と受ける側が別の意味に取った | API のスキーマを定めて検証する。状態のスナップショットを段階配布する |
| Datadog 2023 [11] | OS のパッケージ更新 | 自社の段階配布（blue/green と自動巻き戻し）を通らない経路 | その経路を止め、同種を監査 |

言えること：

- 上の 8 件はすべて、**実行コードの配布は段階的だったのに、コードの挙動を決めるデータは一斉だった**（または段階配布の外にあった）と事業者自身が書いている。Cloudflare [22][24] と Google [13] は、対策としてこの対比を明示している
- 互換性検査の欠落は 2 通りある：(a) 作る側と読む側の取り決めの食い違い（CrowdStrike の項目数、Cloudflare 2026 のフラグ、Cloudflare 2024 の空設定の意味）、(b) 読む側が持つ上限の超過（Cloudflare 2025-11 の 200 個、Kinesis のスレッド数、DynamoDB 2015 の応答時間）
- 読む側の失敗時の挙動が被害の大きさを決めた：落ちる（CrowdStrike、Google 2025、Cloudflare 2025-11）、全部通す（Cloudflare 2024-11）。どちらも事故になっており、「失敗時は通す」が常に安全とは言えない。事業者の対策は「既知の良い版で動き続ける」に寄っている [22][24]

言えないこと：

- 段階配布をしていれば防げた、とは報告からは断定できない。Slack 2022 [19] は 25% の段階を前の週に 2 回通しており、PagerDuty [25] は 1%→75% の段階配布の途中で起きた。段階の間に見る指標と、時間帯・負荷の条件が合っていなければ、段階は素通りする

### 4.5 分析 4：事後報告を読むときの注意

- **自己申告である**。原因の切り方、責任の置き方、書かないことは事業者が選ぶ。Facebook 2021 [8] は停止時間も利用者数も書いていない。Cloudflare 2023 [16] は施設事業者の行動について「未確認」「従業員の非公式な話」と断っている
- **数字の範囲を確かめる**。「〇時間」はどの指標のどの区間か。Google 2025 [13] は速報の「3 時間」と一覧上の最終回復 18:18 が並ぶ。Google 2020 [20] は同じページに 47 分・50 分・別の時刻が出る。GitLab [1] は損失の窓を 2 通りに書いている。AWS 2025 [7] は「全体」と個別サービスで終了時刻が違う
- **「データ損失なし」の範囲**。Roblox [9]・GitHub 2021 [26] は損失なしと書くが、Cloudflare 2023 [16]・2024 [15] のようにログは失われている件がある。何のデータについての「なし」かを読む
- **分母が書かれない**。AWS の各報告 [2][4][5][6][7] は顧客数や要求数をほぼ書かない。Atlassian [10] の「99.6% は影響なし」のように、分母の選び方で印象は変わる
- **公開時点で未完の報告がある**。GitHub 2021 [26] は根本原因を調査中、Google 2025 [13] は追加の分析を予告。速報と最終版で数字が変わりうる
- **再発防止策は約束であり、実施の確認ではない**。Cloudflare は 2025-11 [14] のあとの対策が 2025-12 [22] までに終わっていなかったと自分で書いている
- **公開日がページにない報告がある**（AWS の message ページ [2][4][5][7]）。引用するときは「公開日の記載なし」と書く
- **報告を出す事業者に偏る**。詳しい報告を出すのは一部の事業者で、型の件数は「公開されやすさ」を映す。型の比率を業界全体の頻度として読まない
- **書籍の事例は事後報告ではない**。SRE 本 26 章 [21] は教訓のために選ばれた成功例で、原因の記述は薄い

## 7. 設計レビューで問うこと（分析 3）

| 型 | 問い | なぜ問うか | 危ない兆候 |
|---|---|---|---|
| A | コードの挙動を変えるデータ（設定、ルール、ポリシー、特徴量、割当）は、どの経路で、何秒で、どこまで届くか | コードは段階的でも、データは数秒で全体に届いていた [13][14][22] | 「設定変更なのでリリースではない」 |
| A | そのデータを読む側は、項目数・大きさ・空・重複をどこで検査し、不正なら何をするか | 検証器と読む側が別の前提だった [12]。上限超えで落ちた [14] | 検査が作る側にしかない。読む側が落ちる |
| A | 「空」「値なし」「0」は、作る側と読む側で同じ意味か | 空の設定が「全員」になった [15]。値なしのフラグが「全件」になった [23]。使用量 0 が割当の引き下げになった [20] | 既定値の意味が文書にない |
| A | 自分たちの配布の仕組みを通らずに本番を変える経路はないか（OS の自動更新、基盤側の自動化、機能フラグ） | 自社の段階配布を通らない更新が 5 リージョンを同時に落とした [11] | 「それは基盤側の話」 |
| A | 段階配布の各段で何を見て次へ進むか。その指標は、負荷の高い時間帯の問題を拾えるか | 同じ 25% が 2 回通って 3 回目に倒れた [19]。段階の途中で起きた [25] | 「エラー率が上がらなければ進む」だけ |
| B | この基盤が 1 時間止まったら、止まるサービスはどれか。その一覧は誰が持っているか | 高可用のはずのサービスが、単一拠点の Kafka に依存していた [16] | 依存の一覧がない。「分析用だから止まっても平気」 |
| B | 「止まってもよいはず」の依存（分析、ログ、計測）は、実際に止めて確かめたか | ベストエフォートのはずの送信が Web サーバーを塞いだ [5] | 非同期のつもりで同期の待ちがある。バッファに上限がない |
| B | 基盤の中で、全体で 1 つしかないものは何か（メタデータ、メンバーシップ、DNS の管理、合意クラスタ） | 1 つのメタデータサービス [4]、1 つの Consul [9]、1 つの DNS レコード [7] | 「そこは落ちない前提」 |
| C | 監視・警報・展開・状況ページ・顧客への連絡は、いま守ろうとしている基盤なしで動くか | 状況ページが自分の基盤に依存していた [2][5][13]。監視が見えなくなった [6][9][18] | 監視が本番と同じクラスタ・同じネットワーク・同じ認証 |
| C | 予備の道具と非常時の入口を、最後に使ったのはいつか | 予備の投稿道具は使い慣れておらず遅れた [5]。入館に時間がかかった [8] | 「手順書はある」 |
| C | 顧客の連絡先や識別子は、消えうる対象の外にも持っているか | サイトと一緒に連絡先が消え、問い合わせフォームも使えなかった [10] | 連絡先が製品のデータの中だけにある |
| D | 自動のフェイルオーバーや修復は、どの範囲までを自分で変えてよいか。切り替えた先の構成で、アプリは動くか | 設定どおりに昇格したが、アプリは耐えられなかった [3] | フェイルオーバーの試験が DB 単体。アプリを通していない |
| D | ヘルスチェックは何を見て不健全と判定するか。依存先の障害で、全台が同時に不健全にならないか | 依存先を見るヘルスチェックが全台を外した [7][28]。自分を取り下げた [8] | ヘルスチェックが DB や設定の取得に依存。1 回に外せる量に上限がない |
| D | 部分故障（遅い、片方向だけ通らない）で、合意や選出はどう振る舞うか | 生死の 2 値を前提にした仕組みが止まった [17] | 試験が「ノードを落とす」だけ |
| E | 群の大きさ・顧客数・データ量に比例して増える資源は何か。上限までの残りを監視しているか | スレッド数 [5]、メンバーシップの大きさ [4]、バッファ数 [15]、空き一覧 [9] | 上限が OS や製品の既定値のまま。誰も値を知らない |
| E | 全クライアントが同時に再接続・再試行したら、何が起きるか。乱数つきの後退はあるか。流入を絞る手段はあるか | 再試行が過負荷を固定した [4][6][13]。絞ってから少しずつ戻した [19][8] | 再試行に上限も乱数もない。絞るスイッチがない |
| E | キャッシュが空の状態で、平常のピークを受けきれるか。空から立ち上げた実績はあるか | キャッシュが冷えて DB が倒れ、埋め直せなくなった [19][28]。空からの起動の道具がなかった [9] | 「キャッシュは落ちない」。キャッシュミス時の問い合わせの重さを測っていない |
| E | 全面再起動にどれだけかかるか。最後に測ったのはいつか | 長年再起動しておらず、想定より長かった [2]。1 時間に数百台しか戻せなかった [5] | 全面再起動をしたことがない |
| F | 最後に本番相当のデータを復元したのはいつで、何時間かかったか。バックアップの失敗は誰に届くか | バックアップは失敗し続け、通知は届いていなかった [1] | 「バックアップは取っている」。復元の所要時間を誰も言えない |
| F | 一部の顧客・一部の表だけを、ほかに影響なく戻せるか。その手順を演習したか | マルチテナントの保存先から 1 顧客ずつ取り出すのに最長 14 日 [10] | 復元の単位が「全体」しかない |
| G | 破壊的な操作は、対象の種類と数をどう確かめるか。速度と下限の歯止めはあるか。取り消せるか | ID の種類を確かめない API [10]。下限を割る削除を止めない道具 [2]。現用を消す掃除 [7] | 同じ API が複数の種類の ID を受ける。ソフトデリートがない。検証環境に本番の ID がない |
| H | 「独立している」と言う単位（リージョン、セル、拠点）が共有しているものは何か（更新の時刻、設定の出どころ、全世界複製の表、認証） | 接続のないリージョンが、更新窓を共有していた [11]。メタデータの全世界複製 [13] | 「リージョンは独立なので」 |

## 8. ケーススタディで測れること・測れないこと

測れること（PostgreSQL 18、Redpanda／Kafka 4.x、Debezium 3.x、ClickHouse、DuckDB、CockroachDB の範囲で、小さく再現できるもの）：

- **型 F**：`pg_dump`／ベースバックアップ＋WAL からの復元にかかる時間を、データ量を変えて測る。WAL アーカイブなしで複製が遅れたとき、作り直しになることを再現する（GitLab [1] の構図）
- **型 E**：キャッシュを空にしたときの DB の負荷を、キャッシュミス時の問い合わせの形（キーで 1 行／全シャードに散る）ごとに測る（Slack [19] の構図）。再試行に乱数つきの後退がある場合とない場合で、回復までの時間を比べる
- **型 A**：下流（Debezium → Kafka → ClickHouse）で、上流のスキーマや設定が変わったとき（列の追加、行の重複、空）に、読む側が落ちるか・通すか・前の版で続けるかを確かめる。ClickHouse のメタデータ問い合わせを、データベース名で絞る場合と絞らない場合で比べる（Cloudflare [14] の構図）
- **型 B／E**：Kafka／Redpanda でプロデューサを要求ごとに作ったとき、ブローカーのメモリがどう伸びるかを測る（PagerDuty [25] の構図。版による違いを記録）
- **型 D**：CockroachDB や PostgreSQL の複製で、ノードを落とすのではなく、遅延や片方向の遮断を入れたときの挙動（Cloudflare 2020 [17] の構図）
- **型 G**：ソフトデリートと即時削除で、誤削除からの復旧手順と所要時間を比べる

測れないこと：

- 数万ノード、数百万バッファといった規模で初めて現れる崖（スレッド数、メンバーシップの大きさ）。構図は示せても、閾値は示せない
- 組織の側の欠陥（依頼の伝達、レビューが入力データを見ない、責任者がいない）
- クラウド事業者の内部（DNS の自動化、Transit Gateway、Service Control）。公式文書と事後報告に基づく説明に留める
- 事後報告の数字の再現。事業者の環境は分からないので、同じ数字にはならない

## 10. 結論（スライドに書くこと。箇条書き 15〜30 個、各項目に出典の番号）

1. 大規模な停止の引き金は、多くが故障ではなく変更だった。指定 19 件のうち、ハードウェアや電源の故障が引き金だったのは 3 件 [3][16][17]
2. 引き金は小さい。43 秒の分断が 24 時間 11 分の劣化に [3]、少量の容量追加が終日の障害に [5]、1 つのコマンドの入力誤りが数時間の停止に [2]
3. 被害の大きさを決めるのは、引き金ではなく、広げる側の設計。型は 8 つほどにまとまる（§4.3）
4. 設定・ルール・ポリシーはデータだが、コードの挙動を変える。コードは段階配布、データは数秒で全体、という非対称が繰り返し事故になった [12][13][14][22]
5. 事業者は事故のあと、設定にも段階配布・健全性の確認・巻き戻しを入れると約束している [12][13][22][24]
6. 作る側と読む側の取り決めの食い違いが事故になる：項目数 21 対 20 [12]、空の設定の意味 [15]、値なしのフラグの意味 [23]、使用量 0 の意味 [20]
7. 読む側は自分で検査する。自社が作ったデータでも、外から来た入力と同じに扱う [14]
8. 読む側の失敗時の挙動は、設計して決める。拒んで全停止した例 [13] と、通して下流が倒れた例 [15] の両方がある。対策は「既知の良い版で続ける」に寄っている [22][24]
9. 段階配布は万能ではない。段階の間に何を見るかが合っていなければ素通りする [19][25]
10. 共通基盤は、全サービスの共通の故障点になる。1 つの Consul [9]、1 つのメタデータサービス [4]、1 つの DNS レコード [7]
11. 事業者の対策は分割に向かう：セル、専用クラスタ、利用者ごとの群 [2][4][5][9]
12. 「止まってもよいはず」の依存が本流を止める。分析用の送信が認証を止めた [5]、分析用の機能が通知を止めた [25]、ログ基盤が制御系を止めた [16]
13. 監視・状況ページ・サポート窓口が、壊れた基盤の上にあった件が 9 件ある [2][5][6][8][9][13][18][20][25]。障害のときに見えない・伝えられない
14. 安全のための自動化が被害を広げる。自動昇格 [3][17]、ヘルスチェック [7][28]、設定の自動修正 [27]、失敗時の安全装置 [15]、停止スイッチ [22]
15. 自動のフェイルオーバーは、切り替えた先でアプリが動くことまで確かめて初めて完成する [3]
16. 部分故障（遅い、片方向だけ通らない）は、落ちるより扱いにくい [17]
17. 過負荷には、引き金を取り除いても自力で戻らない状態がある。流入を絞り、少しずつ戻すしかなかった [4][8][19][27]
18. 再試行は、乱数つきの後退がなければ過負荷を固定する [4][6][13]
19. キャッシュが性能の前提になっていると、冷えたときに DB が倒れ、埋め直せない [19][28]
20. 群の大きさに比例して増える資源には崖がある。スレッド数 [5]、メンバーシップの大きさ [4]、バッファ数 [15]
21. バックアップがあることと、復元できることは別。日次のバックアップは失敗し続け、通知は届いていなかった [1]
22. 復元は、定期的に実演して初めて当てになる [21]。長引いた件は、空から・大量に戻す手順を試していなかった [9][10][3]
23. マルチテナントでは「一部の顧客だけを戻す」手順が要る。なければ最長 14 日 [10]
24. 削除には猶予を置く。事業者は事故のあとソフトデリートを全体に入れると約束した [10]。SRE 本は 3 層の最初に置く [21]
25. 破壊的な操作の道具と API に、対象の種類の検査・速度の制限・下限の歯止めを入れる [2][10][23]
26. 「独立」と言う単位が何を共有しているかを問う。更新の時刻 [11]、全世界複製の表 [13]、単一拠点の部品 [16]
27. 事後報告は自己申告。数字の区間と分母、「損失なし」の範囲、公開時点で未完かどうかを確かめて引用する [8][13][20][26]
28. 再発防止策は約束であり、実施の確認ではない。対策が終わる前に同じ型が再発した例がある [14][22]
