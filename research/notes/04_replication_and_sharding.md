## 1. 問い（このノートが答えること。対応する Part）

対応する Part：8（ステップ 6「複製と分割をどう決めるか」）。地図は DDIA 2e の 6 章（レプリケーション）と 7 章（シャーディング）。

このノートが答える問い：

1. 単一リーダー・マルチリーダー・リーダーレスは、何を得て何を失う選択か

## 2. 標準・定義（節番号）

複製と分割そのものを定めた公的な標準は見つからなかった（SQL 標準は複製を扱わない。これも結論として記録する）。定義の出どころは原論文と製品の公式文書になる。

| 用語 | 定義（自分の言葉） | 出どころ |
| --- | --- | --- |
| クォーラム（N・R・W） | N 個の複製のうち、書き込みは W 個、読み取りは R 個の応答で成功とする。R + W > N なら読みと書きの集合が必ず重なる。応答の遅さは R（W）個のうち最も遅い複製で決まるので、R と W は N より小さくするのが普通 | Dynamo 論文 4.5 節 [1] |
| sloppy quorum | 厳密なクォーラムの構成員にこだわらず、優先リストのうち「健全な最初の N 個」で読み書きする。障害や分断のあいだも書き込みを受けるため | Dynamo 論文 4.6 節 [1] |
| hinted handoff | 本来の担当が落ちているとき、代わりの節点が「本来の宛先」の印をつけて預かり、復帰後に渡す | Dynamo 論文 4.6 節 [1] |
| ベクタークロック | (節点, カウンタ) の組の並び。版どうしの因果（先祖か、並行か）を判定する。並行な版は消さずに両方返し、読み手が統合する | Dynamo 論文 4.4 節 [1] |
| 反エントロピー（Merkle 木） | 複製どうしでハッシュ木の根から比べ、ずれたキーだけを同期する | Dynamo 論文 4.7 節 [1] |
| コンシステントハッシュ・仮想ノード | ハッシュ空間を環にして節点を置き、節点の増減で動くキーを隣だけに抑える。1 台に複数の位置（仮想ノード）を持たせて偏りをならす | Dynamo 論文 4.2 節 [1]。原典（Karger ほか 1997）は記憶・要確認 |
| 同期の複製（PostgreSQL） | 書き込みトランザクションのコミットが、プライマリとスタンバイの両方で WAL がディスクに書かれた確認を待つ | PostgreSQL 18 文書 26.2.8 節 [3] |
| 結果整合（スタンバイの読み取り） | スタンバイのデータは届くまでに測れる遅れがあり、プライマリに対して結果整合 | PostgreSQL 18 文書 26.4 節（Hot Standby）[7] |
| STONITH・フェンシング | 昇格のあと、旧プライマリに「もうプライマリではない」と伝える（止める）仕組み。両方がプライマリだと思う状態を防ぐ | PostgreSQL 18 文書 26.3 節 [5] |
| RPO・RTO | RPO は失ってよいデータ量（時間で測る）、RTO は復旧までの時間 | Aurora ユーザーガイド [16] |
| セル | ワークロード一式の独立した複製。ほかのセルと状態を共有せず、全体の要求の一部だけを受ける | AWS セルベースアーキテクチャの指針 [26] |
| サイロ・プール・ブリッジ | テナントに専用の資源を与える／共有する／部分ごとに混ぜる | AWS SaaS Lens [25] |

読み取りの異常の名前（自分の書き込みが読めない＝read-your-writes の違反、時間が戻る＝monotonic reads の違反、因果が崩れる＝consistent prefix の違反）は DDIA 6 章の整理に従う。原典（Terry ほか 1994 のセッション保証）は記憶・要確認。

Dynamo 論文の本文で確かめた、設計の前提：

- 目標は「常に書き込める」データストアで、結果整合を受け入れる（2 節・4 節）。応答時間の SLA は 99.9 パーセンタイルで述べる（2.2 節）[1]
- よく使う設定は (N, R, W) = (3, 2, 2)（6 節）[1]
- ベクタークロックは伸びるので、組の数がしきい値（例として 10）に達すると最も古い組を捨てる。これで因果の判定が不正確になりうる、と論文自身が書いている（4.4 節）[1]
- 実運用で版が分かれた頻度：ある 24 時間で、要求の 99.94% は 1 版だけ、0.00057% が 2 版、0.00047% が 3 版を見た（6.3 節）[1]。「衝突はまれ」は Amazon の買い物かごの負荷での測定であり、一般の保証ではない

**DynamoDB は Dynamo 論文の実装ではない**。2022 年の USENIX ATC 論文は、DynamoDB が Dynamo と名前の大半を共有するが構造はほとんど共有しない、と自ら書いている（1 節）[2]。本文で確かめた違い：

| 論点 | Dynamo（2007 年の論文）[1] | DynamoDB（2022 年の論文）[2] |
| --- | --- | --- |
| 複製の方式 | リーダーレス。sloppy quorum と hinted handoff | パーティションごとの複製グループ。Multi-Paxos でリーダーを選ぶ |
| 書き込みの確認 | W 個の節点の応答 | 複製の過半（3 つの AZ のうち 2 つ）が WAL に書いたら応答（3 節・6.1 節） |
| 読み取り | R 個から集め、版が分かれていれば全部返す | 強整合の読み取りと書き込みはリーダーだけ。結果整合の読み取りはどの複製でもよい（3 節） |
| 衝突の解決 | ベクタークロック＋利用側の統合（または最後の書き込みが勝つ） | 単一リーダーなので 1 リージョン内では衝突しない |
| リーダーの交代 | 該当なし | リースで保つ。新しいリーダーは、前のリーダーのリースが切れるまで書き込みも強整合の読み取りも受けない（3 節） |
| 運用 | 利用チームが自分で運用する単一テナント | マルチテナントのマネージドサービス |

## 3. 製品ごとの違い（表。公式文書の URL・版・日付）

### 3.1 PostgreSQL 18 のストリーミングレプリケーション（表示上の版は 18.7。2026-11-18 閲覧）

`synchronous_commit` の各値が保証すること（19.5 節「Write Ahead Log」、表 19.1）[4]：

| 値 | コミットが待つもの | プライマリのクラッシュで残るか | スタンバイの PostgreSQL のクラッシュで残るか | スタンバイの OS のクラッシュで残るか | スタンバイで読めるか |
| --- | --- | --- | --- | --- | --- |
| `remote_apply` | スタンバイが受け取り、フラッシュし、**再生（適用）した**こと | 残る | 残る | 残る | 読める |
| `on`（既定） | スタンバイが受け取り、**ディスクにフラッシュした**こと | 残る | 残る | 残る | 保証しない |
| `remote_write` | スタンバイが受け取り、OS に書いたこと（フラッシュは待たない） | 残る | 残る | 残らないことがある | 保証しない |
| `local` | 手元の WAL のフラッシュだけ | 残る | 保証しない | 保証しない | 保証しない |
| `off` | 何も待たない | 直近の分を失うことがある | 保証しない | 保証しない | 保証しない |

- `off` で失いうるのは、最大で `wal_writer_delay` の 3 倍の時間ぶんのコミット。ただし `fsync` を切るのと違い、データベースの不整合は起きない（失われたトランザクションは、きれいに中断されたのと同じ状態になる）[4]
- **`synchronous_standby_names` が空（既定）のとき、意味のある値は `on` と `off` だけ**。`remote_apply`・`remote_write`・`local` は `on` と同じ「手元のフラッシュ」になる [4]。つまり `synchronous_commit = on` が既定でも、スタンバイ名を設定しなければ複製は非同期のまま
- ストリーミングレプリケーションは既定で非同期（26.2.5 節）。遅れは、スタンバイに十分な性能があれば通常 1 秒未満、と文書は書く（保証ではない）[3]

`synchronous_standby_names` の書き方（19.6.2 節）[6]：

| 書き方 | 意味 |
| --- | --- |
| `FIRST 2 (s1, s2, s3)` | 優先順位方式。並びの前から 2 台を同期スタンバイにする。落ちたら次の順位が直ちに代わる |
| `ANY 2 (s1, s2, s3)` | クォーラム方式。並びのうちどれか 2 台の応答でコミットが進む |
| `s1, s2` | `FIRST 1 (s1, s2)` と同じ |
| `*` | どのスタンバイ名にも合う |
| 空（既定） | 同期の複製を使わない。コミットは複製を待たない |

同期にしたときに遅くなるもの・止まるもの（26.2.8 節）[3]：

- 待つのは**書き込みトランザクションのコミット**。待ち時間の下限はプライマリとスタンバイの往復時間。読み取り専用トランザクションとロールバックは待たない。サブトランザクションのコミットも待たない。二相コミットは prepare も commit も待つ
- 待っているあいだ、資源は使わないが**トランザクションのロックは保持したまま**。不用意な同期化は応答時間と競合を増やす、と文書が書いている（26.2.8.3 節）。重要な変更だけ同期にし、残りは非同期にする使い分けを文書が例示している
- **同期スタンバイが必要な数だけいなければ、コミットは完了しないまま待ち続ける**（26.2.8.4 節）。タイムアウトの記述はない。対処は、候補のスタンバイを複数名指しておくこと、どうしても足りなければ同期の数を減らす（または無効にする）設定を再読み込みすること
- 待っている最中にプライマリが落ちて復旧すると、待っていたトランザクションは**コミット済みとして扱われる**（26.2.8.1 節）。利用側は「応答が来なかった＝書き込まれていない」とは言えない
- 一部のトランザクションは、プライマリでコミット済みに見えてもスタンバイではまだ見えないことがある（`remote_apply` 以外）

フェイルオーバーと昇格（26.3 節）[5]：

- **PostgreSQL は、プライマリの障害を検知してスタンバイに知らせるシステムソフトウェアを提供しない**。外部の道具に任せる、と文書が明記している
- 昇格は `pg_ctl promote` または `pg_promote()`
- 旧プライマリが再起動してくる場合、それがもうプライマリでないと知らせる仕組み（STONITH）が要る。両方がプライマリだと思う状態は、混乱と最終的なデータの喪失につながる、と文書が書いている
- 昇格後は 1 台だけで動く「縮退した状態」。元に戻すにはスタンバイを作り直す。大きなクラスタでは `pg_rewind` で速くできる
- 監視役（witness）は不適切なフェイルオーバーの一部を防げるが、複雑さに見合うだけの注意と試験が要る
- 定期的な切り替え（スイッチオーバー）は、フェイルオーバーの仕組みの試験になる。手順は文書にしておく、と勧めている

`pg_rewind`（PostgreSQL 18）[8]：

- 系列（タイムライン）が分かれたあと、データディレクトリをもう一方に合わせ直す。変わったブロックだけ写すので、差が小さければ作り直しより速い
- 前提：`wal_log_hints` が有効、またはデータチェックサムが有効（文書は initdb の既定と書いている）。`full_page_writes` は `on`。対象はきれいに停止していること
- **旧プライマリだけにあった、分岐後の変更は、ソース側の状態で上書きされて残らない**（手順の説明からの帰結。文書は「失われる」という語は使っていない）。非同期の複製で昇格したとき、応答済みのコミットがここで消える
- 途中で失敗すると、対象のデータディレクトリは復旧できない状態になりうる。その場合は新しいバックアップから作り直す

複製の方式の比較表（26.1 節、表 26.1）[9]：WAL 送信は「複数のサーバーを待たない」は同期オフのときだけ、「プライマリの障害でデータを失わない」は同期オンのときだけ成り立つ。同期のマルチマスターは本体にはなく、非同期のマルチマスターは衝突の解決が要る。

スタンバイでの読み取り（26.4 節）[7]：再生と衝突する問い合わせは、遅延の上限（`max_standby_streaming_delay`、既定 30 秒 [6]）を超えると取り消される。`hot_standby_feedback`（既定 off [6]）は取り消しを減らすが、プライマリの不要行の掃除が遅れて肥大化しうる。

### 3.2 複製の方式と読み取りの整合性（製品の比較）

| Redpanda 26.2 | パーティションごとの Raft グループ | — | `acks=all` は過半数が書き込み、既定では fsync してから応答 | [23][24] |

Aurora のレプリカの遅れが小さいのは、共有ストレージを読むから。それでも「遅れゼロ」とは書いていない。書き込み直後の読み取りをレプリカに送れば、自分の書き込みが読めないことは起こりうる。

## 4. 事故・失敗例（一次報告）

原因を「どの取り決めの欠陥か」で整理する。事実は各社の事後報告から。取り決めへの当てはめは、このノートの整理であり、各社の公式な結論の言い換えではない。

### 4.1 GitHub 2018-10-21（劣化 24 時間 11 分）[29]

事実：

- 22:52 UTC、故障した 100G の光学機器を交換する定例の保守で、米国東海岸のネットワーク拠点と東海岸の主データセンターの接続が 43 秒切れた
- MySQL の構成管理（Orchestrator、Raft で合意）で、主データセンターの節点がリーダーを降り、西海岸と東海岸のパブリッククラウドの節点がクォーラムを作って、書き込み先を西海岸に切り替えた
- 接続が戻ると、アプリケーションは直ちに西海岸の新しいプライマリへ書き始めた
- 東海岸には西海岸に複製されていない数秒ぶんの書き込みが残り、西海岸にも新しい書き込みが入った。**両方が相手にない書き込みを持った**ので、安全に戻せなかった。最も忙しいクラスタで、該当の時間帯の書き込みは 954 件
- 東海岸のアプリケーションは、大陸横断の遅延で DB を呼ぶ前提では動けなかった
- 方針は、使いやすさと復旧時間よりもデータの完全性を優先すること。バックアップ（4 時間ごと、遠隔に保管）から数テラバイトを復元するのに数時間かかった
- 今後の対応：リージョンをまたぐプライマリの昇格を防ぐよう Orchestrator の設定を直す、障害注入の試験に投資する、など

どの取り決めの欠陥か：

| 取り決め | 欠陥 |
| --- | --- |
| 昇格してよい範囲 | 非同期の複製なのに、リージョンをまたぐ自動昇格を許していた。合意の仕組み（Raft）は「誰がリーダーか」を正しく決めたが、「昇格先がどこまで追いついているか」は決めていない |
| 障害の判定 | 43 秒の分断を障害と見なして昇格した。自動昇格の速さは、短い分断での誤昇格と引き換え |
| 旧プライマリの書き込みの扱い | 未複製の書き込みをどう戻すかの手順が事前になく、事後に手作業で突き合わせた |
| アプリケーションの配置 | DB の主が遠くへ移っても動く、という前提が成り立っていなかった |

### 4.2 GitLab.com 2017-01-31（データベースの停止と約 6 時間ぶんの喪失）[30]

事実：

- 負荷の急増（スパムの疑い）でセカンダリの複製が遅れ、必要な WAL セグメントがプライマリから消えていて複製が止まった。**WAL のアーカイブは使っていなかった**ので、セカンダリは手で作り直すしかなかった
- 作り直しの途中（`max_wal_senders` を 3 から 32 に、`max_connections` を 8000 から 2000 に変更）、`pg_basebackup` が黙って待つ挙動を止まったと判断し、セカンダリのデータディレクトリを消すつもりで**プライマリのものを消した**。約 300 GB が消えた
- 日次の `pg_dump` は、9.6 のデータベースに 9.2 の `pg_dump` を使っていて失敗し続けていた。失敗の通知メールは DMARC の設定がなく受信側で拒否されていた。Azure のディスクスナップショットはデータベースサーバーでは無効だった
- たまたま約 6 時間前に手で取った LVM スナップショットから復元。遅いディスクのため写しに約 18 時間。17:20 UTC 以降のデータ（プロジェクト約 5,000、コメント約 5,000、ユーザー約 700 の見積もり）を失った
- 根本原因の 1 つとして、バックアップの試験に責任を持つ者がいなかったことを挙げている

どの取り決めの欠陥か：

| 取り決め | 欠陥 |
| --- | --- |
| 複製の役割 | 複製はフェイルオーバーのためのもので、災害復旧の手段ではない（報告自身がそう書く）。削除はそのまま複製され、今回は両方の節点が空になった |
| WAL の保持 | アーカイブもレプリケーションスロットもなく、スタンバイが遅れると追いつけなくなる構成だった（スロットは今回の PostgreSQL 18 の文書 26.2.6 節の機能。当時の版での可否は未確認） |
| 復元の検証 | バックアップは「取っているつもり」で、復元を試していなかった。失敗の通知も届いていなかった |
| 危険な操作の手順 | どのホストで作業しているかを確かめる手順がなく、本番の主と副で同じ操作ができた |

### 4.3 Cloudflare 2020-11-02（API とダッシュボードの劣化 6 時間 33 分）[31]

事実：

- 14:43 UTC、ネットワークスイッチが**部分的に動く状態**になった。一部の制御プロトコル（LACP・BGP）には応答するが、ほかには応答せず、パケットも一部しか転送しない。完全に落ちていれば対のスイッチに切り替わったはずだった
- 3 節点の etcd（Raft）で、節点 1 はリーダー（節点 3）に届かないが節点 2 には届く。節点 2 は節点 3 に届く。節点 1 は選挙を繰り返し、リーダーが定まらず、クラスタは読み取り専用になった
- etcd に頼っていた 2 つのデータベースクラスタが健全なプライマリを確認できず、自動化が同期レプリカを昇格した。**昇格そのものはエラーもデータの喪失もなかった**
- しかし、クラスタ管理の欠陥で、昇格のたびに全レプリカの作り直しが必要だった。認証用のデータベースは読み取りの負荷をレプリカに逃がしていたので、レプリカがないあいだプライマリが過負荷になった。これが主な影響
- 復旧は、最初のレプリカが作り直されて戻った 21:20 UTC
- 対応：昇格後にレプリカを作り直さずに済むよう直す、読み取りを別データセンターのレプリカへ自動で向ける、自動修復の設定を見直す（少なくとも 1 つのデータベースでは、あれほど速い昇格は元の問題より害が大きい）
- 報告は「ビザンチン障害」と呼ぶが、追記で、分散システムの研究者からは**欠落（omission）障害**と呼ぶほうが適切との指摘があったと書いている

どの取り決めの欠陥か：

| 取り決め | 欠陥 |
| --- | --- |
| 障害の型の想定 | 「落ちるか、動くか」を前提にした冗長化。部分的に動く機器は、切り替えも合意も乱す |
| 昇格の引き金 | 「調整サービスが使えない」ことを「プライマリが落ちた」ことと同じに扱って昇格した。プライマリ自身は健全だった |
| 昇格の後始末 | 昇格の費用（レプリカの作り直し）が大きいのに、昇格を軽い操作として自動化していた |
| 読み取りの容量 | 読み取りをレプリカに逃がす設計は、レプリカが消えるとプライマリの容量不足になる。レプリカは可用性の冗長ではなく、容量の一部になっていた |

### 4.4 Jepsen の検証（事故ではなく、検証で見つかった欠陥）

| 対象（版・日付） | 見つかったこと | 出典 |
| --- | --- | --- |
| Redpanda 21.10.1（2022-04-29 公開。21.10.1〜21.11.2 と開発版を試験。Redpanda Data の資金による） | 既定で重複書き込み（冪等性がサーバー側で無効だった）。冪等性を有効にしても重複（21.10.2 で修正）。オフセットの不整合（21.10.3 で修正）。トランザクションで中断された読み取りと書き込みの喪失（21.11.15 で修正）。応答済みのメッセージがどの読み手にも届かない事象は報告時点で未解決。あわせて、Kafka の `acks=all` は既定で fsync しないこと、自動コミットの既定がメッセージを失いうること、Kafka のトランザクションの文書が自己矛盾していることを指摘 | [32] |

Azure の指針の「テナントごとのテーブルはアンチパターン」と、Citus のスキーマ単位のシャーディングは、同じ「スキーマ分離」に見えて前提が違う。前者は 1 つのデータベースにテナント数ぶんのテーブルを詰める話、後者はスキーマを分散の単位にして節点へ配る話である。Citus の文書も、行ベースのシャーディングより 1 節点あたりのテナント数は少なくなると書いている [27]。

## 6. 設計判断の分かれ目（何を選ぶと何を得て何を失うか。表）

### 6.1 リーダーの置き方

| 選択 | 得るもの | 失うもの | 向く場面 |
| --- | --- | --- | --- |
| 単一リーダー（PostgreSQL、Aurora、DynamoDB の 1 パーティション） | 書き込みの衝突がない。順序が 1 本 | 書き込みはリーダーの容量と所在に縛られる。リーダー交代の取り決め（検知・昇格・遮断）が要る | 既定の選択。制約と一意性が要るデータ |
| マルチリーダー（DynamoDB global tables の MREC など） | 各拠点で書ける。拠点間の分断中も書ける | 衝突の解決が要る。「最後の書き込みが勝つ」は**応答済みの書き込みを黙って捨てる**。トランザクションと一意性が拠点をまたいで成り立たない | 拠点ごとに書き込む項目が分かれている、または上書きで失ってよいデータ |
| リーダーレス（Dynamo 型） | 節点の障害でも切り替えなしで読み書きできる。遅い節点を待たない | sloppy quorum では R + W > N でも古い値を読みうる。並行な版の統合を利用側が負う | 可用性を最優先し、統合の規則を書けるデータ（買い物かごの和集合など） |
| 合意に基づく複製（Raft・Paxos：CockroachDB、Spanner、Redpanda、DynamoDB、KRaft） | リーダーの交代が取り決めの中に入っており、過半数が生きていれば応答済みの書き込みを失わない | 過半数を失うと書けない。書き込みは過半数への往復を待つ。実装の欠陥は検証で見つかる（4.4 節） | 自動のフェイルオーバーで書き込みを失いたくないとき |

### 6.2 同期か非同期か

| 選択 | 得るもの | 失うもの |
| --- | --- | --- |
| 非同期（PostgreSQL の既定） | コミットが速い。スタンバイが落ちても書ける | 昇格で、応答済みのコミットを失いうる（RPO > 0） |
| 同期・1 台だけ名指し | 応答済みのコミットは 2 台にある | そのスタンバイが落ちると**書き込みが止まる**。可用性が 2 台の積になる |
| 同期・`ANY 1 (s1, s2)` | 1 台落ちても書ける。応答済みのコミットは少なくとも 2 台にある | スタンバイが 2 台要る。コミットは速いほうの往復を待つ |
| `remote_apply` | 同期スタンバイでは、コミット直後に自分の書き込みが読める | 再生を待つぶん、コミットがさらに遅い。再生が詰まると書き込みが遅れる |
| トランザクションごとに使い分け | 重要な書き込みだけ遅くなる | どれが重要かをアプリケーションが決めて設定する責任 |

### 6.3 古い読み取りへの対処

| 選択 | 得るもの | 失うもの |
| --- | --- | --- |
| 書き込み直後の読み取りはリーダーへ送る | 自分の書き込みが読める | リーダーの負荷。経路の出し分けをアプリケーションが持つ |
| 同じ利用者は同じレプリカへ固定する | 時間が戻らない | レプリカが落ちたときの扱い。負荷の偏り |
| 古さを明示して読む（follower reads、stale read） | 遅延と負荷を下げ、「何秒前の一貫した時点か」が分かる | 最新ではない。読み取り専用に限られる |
| 強整合の読み取りを指定する（DynamoDB `ConsistentRead`） | 最新が読める | 料金が 2 倍。GSI では使えない |
| 読み取りを同期で待たせる（`remote_apply`） | レプリカでも最新 | 書き込み側が遅くなる |

### 6.4 フェイルオーバーの自動化

| 選択 | 得るもの | 失うもの |
| --- | --- | --- |
| 手動の昇格 | 誤昇格がない。人が状況を見て決める | RTO が人の反応時間になる。手順が古びる |
| 自動の昇格（外部の道具） | RTO が短い | 短い分断や部分障害での誤昇格（4.1・4.3 節）。フェンシングがなければスプリットブレイン |
| 合意に組み込まれた交代 | リースや任期番号で、旧リーダーの書き込みが通らない | 過半数が要る。リースは時計の進み方への仮定に頼る |
| リージョンをまたぐ自動昇格 | リージョン障害から自動で戻る | 非同期なら RPO > 0。両側に相手にない書き込みができると、戻すのに日単位（4.1 節） |

### 6.5 シャーディングのキーと方式

| 選択 | 得るもの | 失うもの |
| --- | --- | --- |
| キー範囲 | 範囲の走査が速い。分割点を動かせる | 単調に増えるキーで末尾に書き込みが集中する |
| ハッシュ | 書き込みが散る | 範囲の走査ができない（全シャードに問い合わせる） |
| ハッシュ ÷ 固定数（Kafka のパーティション） | 単純 | 数を変えるとキーの行き先が変わる。減らせない |
| 複合キー（パーティションキー＋ソートキー） | 1 つの利用者の範囲走査は 1 パーティションで済む | 1 つのパーティションキーに負荷が集中すると上限に当たる |
| ローカル索引 | 書き込みが軽く、強整合 | キーを含まない検索が全シャード |
| グローバル索引 | 検索が 1 か所 | 書き込みが重い、または索引が古い |

### 6.6 マルチテナントの分離

| 方式 | 得るもの | 失うもの | 見直しの合図 |
| --- | --- | --- | --- |
| 共有スキーマ（プール。テナント ID の列） | 最も安い。運用の対象が 1 つ | ノイジーネイバー。テナント単位の復元・暗号鍵・所在地の要件に応えにくい。漏えいを防ぐのはアプリケーションと行レベルの制御 | 特定テナントが資源の上限に当たる。テナント単位の復元を求められる |
| スキーマ分離 | テナントごとの論理的な区切り。テナント単位の移動がしやすい | テナント数が増えるとカタログとスキーマ変更の運用が重い | スキーマ変更の所要時間がテナント数に比例して伸びる |
| DB 分離（サイロ） | 強い分離。テナントごとの鍵・バックアップ・版 | 費用が高い。台数ぶんの運用とスキーマ変更の自動化が必須 | 自動化なしでは手に負えない台数になる |
| セルベース（スタンプ） | 障害とデプロイの影響を 1 セルに閉じ込める。セルの最大の大きさが決まるので、試験した規模の外へ出ない | ルーターとコントロールプレーンという新しい共通の依存。セルをまたぐ処理と集計が難しい。テナントの移動の仕組みが要る | 1 回のデプロイの失敗が全テナントに及ぶことを許せなくなったとき |

## 8. ケーススタディで測れること・測れないこと

測れる（WSL の Docker。PostgreSQL 18 のプライマリ＋スタンバイ、Redpanda、Kafka 4.4、CockroachDB）：

| 測ること | 方法の見込み | 対応する主張 |
| --- | --- | --- |
| 同期と非同期のコミット時間の差 | `synchronous_commit` を `off`／`local`／`remote_write`／`on`／`remote_apply` で切り替え、Toxiproxy で往復の遅延を入れる | 待ち時間の下限は往復時間 [3] |
| 同期スタンバイが落ちたときの書き込みの停止 | 同期スタンバイを 1 台名指しして止め、コミットが返らない時間を測る。`ANY 1 (s1, s2)` と比べる | コミットは待ち続ける [3] |
| 昇格で失われた応答済みコミットの件数 | 非同期で書き込み中にプライマリを切り離して昇格。書き手 ID＋連番で、応答済みなのに新プライマリにない件数を数える。同期では 0 になることを確かめる | 非同期の RPO > 0 |
| 自分の書き込みが読めない頻度 | 書き込み直後にスタンバイを読む。再生を遅らせて（`recovery_min_apply_delay` または遅延の注入）、読めなかった割合を測る。`remote_apply` で 0 になるかを確かめる | [4][7] |
| `pg_rewind` で旧プライマリの分岐後の変更が消えること | 分断中に旧プライマリへ書き、巻き戻しの前後で件数を比べる | [8] |
| スプリットブレイン | 遮断なしで昇格し、両方に書けることを示す | [5] |
| パーティション数を増やしたときのキーの行き先 | 同じキーの集合を増加の前後で送り、行き先が変わったキーの割合と順序のずれを数える。Redpanda と Kafka で照合 | [22][24a] |
| 単調なキーとハッシュシャード索引 | CockroachDB で連番のキーと `USING HASH` を比べ、range ごとの負荷の偏りを見る（3 ノードを組める場合） | [10] |
| follower reads の古さ | CockroachDB で `follower_read_timestamp()` の値と、直前の書き込みが見えないことを確かめる | [11] |

実験の注意：

- **Redpanda の開発モードは write caching が既定で有効、fsync も省く** [24]。コンテナの既定の起動方法がこれに当たるなら、耐久性の実験の結果は本番の設定を表さない。起動オプションと設定を記録し、本番モード相当で測る
- Kafka 4.4 の `acks=all` は fsync を条件にしない [21]。Redpanda との比較では、何を待って応答しているかをそろえて書く
- 単一ホストなので、遅延はすべて注入したもの。数値は同一環境内の相対比較にとどめる

測れない（未検証と明記する）：

- リージョンをまたぐ遅延と障害、Aurora・Spanner・DynamoDB の公称の RPO／RTO
- 時計のずれに由来する異常（リースの二重保持など）
- RDS for PostgreSQL のマルチ AZ クラスタで Jepsen が見つけた Long Fork（素の PostgreSQL 18 のスタンバイで起きるかは、起きても確率的で、決定的な実験として組めるかは不明。試すなら「再現できなかった」も結果として書く）
- 部分的に動くネットワーク機器（Cloudflare の型）。Toxiproxy で片方向・一部の経路だけの切断は模擬できるが、実機の故障の再現ではない
- セルベースとマルチテナントの分離の、規模に由来する効果

## 10. 結論（スライドに書くこと。箇条書き 15〜30 個、各項目に出典の番号）

1. 複製の選択は「誰が書き込みを受けるか」（単一リーダー・マルチリーダー・リーダーレス）と「いつ応答するか」（同期・非同期）の 2 つの軸で決める。混ぜて語らない [1][3]
2. Dynamo 論文の設計は「常に書き込める」ことを最優先にした選択で、代わりに結果整合と、並行な版の統合を利用側に負わせた。R + W > N でも、sloppy quorum では最新が読めるとは限らない [1]
3. Dynamo 論文の「版が分かれるのはまれ」（99.94% が 1 版）は、ある 24 時間の Amazon の負荷での測定。一般の保証ではない [1]
4. DynamoDB は Dynamo 論文の実装ではない。パーティションごとに Multi-Paxos でリーダーを選び、3 つの AZ のうち 2 つが書いたら応答する。名前で設計を推測しない [2]
5. PostgreSQL 18 のストリーミングレプリケーションは既定で非同期。`synchronous_commit = on` が既定でも、`synchronous_standby_names` が空なら手元のフラッシュしか待たない [3][4]
6. `synchronous_commit` の 5 つの値は、コミットが「どこまで届いたことを待つか」の違い。`remote_apply` だけが、スタンバイで読めることまで待つ [4]
7. 同期にすると遅くなるのは書き込みのコミットで、下限は往復時間。待つあいだロックを持ち続けるので、競合も増える。読み取り専用とロールバックは待たない [3]
8. 同期スタンバイが足りなくなると、PostgreSQL のコミットは待ち続ける。タイムアウトはない。同期は 2 台以上の候補（`ANY 1 (s1, s2)` など）と組で設計する [3][6]
9. コミットの応答が返らなくても、そのトランザクションは手元ではコミット済みになりうる。「応答がない＝書かれていない」とは言えない [3]
10. PostgreSQL 本体は、障害の検知も、昇格の判断も、旧プライマリの遮断も持たない。外部の道具と手順の取り決めが要る [5]
11. `pg_rewind` は旧プライマリを新しい系列に合わせ直す道具で、旧プライマリだけにあった変更は残らない。非同期で昇格したら、巻き戻す前に差分を保存する [8]
12. 複製の遅延で起きる読み取りの異常は 3 つ：自分の書き込みが読めない、時間が戻る、因果が崩れる。対策は、読み取りの行き先を決めること、または古さを明示して読むこと [7][11][18]
13. 製品の「古い読み取り」の機能は 2 種類ある。最新を保証する機能（DynamoDB の強整合の読み取り、PostgreSQL の `remote_apply`）と、古さを明示して速く読む機能（CockroachDB の follower reads、Spanner の stale read）[4][11][13][18]
14. DynamoDB の GSI は強整合の読み取りができない。索引を読んだ結果で書き込みを決める設計は、古い値に基づく [13]
15. Aurora のリーダーエンドポイントは接続を振り分けるだけで、書き込み直後の読み取りを保証しない。レプリカの遅れは通常 100 ミリ秒よりずっと小さい（公称）が、ゼロではない [14][15]
16. レプリカの読み取りは「古い」だけとは限らない。RDS for PostgreSQL のマルチ AZ クラスタでは、プライマリとセカンダリがトランザクションの順序について食い違う異常が、障害のない状態で見つかった（Jepsen、2025-04-29）[34]
17. GitHub 2018-10：合意の仕組みは正しく動いたが、非同期の複製でリージョンをまたぐ昇格を許していた。43 秒の分断が、24 時間 11 分の劣化と手作業の突き合わせになった [29]
18. GitLab 2017-01：複製はバックアップではない。削除は複製される。5 つの復元手段のうち働いたのは、たまたま手で取ったスナップショットだけだった [30]
19. Cloudflare 2020-11：部分的に動く機器は、冗長化の切り替えも合意も乱す。昇格はデータを失わなかったが、昇格の後始末（レプリカの作り直し）が 6 時間 33 分の劣化の主因になった [31]
20. 3 つの事故に共通するのは、製品の欠陥ではなく取り決めの欠陥：昇格してよい範囲、障害の判定、旧プライマリの扱い、昇格の費用、復元の検証 [29][30][31]
21. フェイルオーバーの自動化は RTO を短くするが、誤昇格と引き換え。Cloudflare は、少なくとも 1 つのデータベースで速すぎる昇格が元の問題より害が大きいと結論した [31]
22. 遮断（フェンシング）は「努力」ではなく「保証」かを問う。Aurora Global Database の文書は、書き込みの遮断が最善努力で、スプリットブレインがありうると明記している。DynamoDB は、前のリーダーのリースが切れるまで新しいリーダーが書き込みを受けない [2][16]
23. リージョンをまたぐ複製の公称値：Aurora Global Database は RPO が通常は秒単位・RTO は分単位、計画的な切り替えは RPO 0。DynamoDB global tables は MREC で RPO が複製の遅れに等しく、MRSC で 0。いずれも公称で、未検証 [16][17]
24. RPO 0 には代償がある。DynamoDB の MRSC はちょうど 3 リージョンが要り、書き込みが遅くなり、TTL・LSI・トランザクションが使えず、作成後にモードを変えられない。Aurora の `rds.global_db_rpo` は、遅れが上限を超えるとプライマリのコミットを止める [16][17]
25. マルチリーダー（MREC）の「最後の書き込みが勝つ」は、応答済みの書き込みを黙って捨てる規則。トランザクションも、実行したリージョンの中でしか原子的でない [17]
26. シャーディングは、キー範囲（走査が速いが、単調なキーで偏る）とハッシュ（散るが、範囲で読めない）の選択。CockroachDB は範囲、DynamoDB はパーティションキーのハッシュ＋ソートキーの範囲 [10][20]
27. 1 つのキーに集中する負荷は、分割しても減らない。DynamoDB の適応キャパシティは熱い項目を別のパーティションに分けるが、1 項目の上限（3,000 RCU／1,000 WCU）は超えられない [20a]
28. Kafka・Redpanda のパーティションは増やせるが減らせない。増やすとキーの行き先が変わり、既存のデータは動かない。キーごとの順序に頼る設計では、最初の数の決め方が後から変えられない制約になる [22][24a]
29. 合意に基づく複製（Raft・Paxos）は、リーダーの交代を取り決めの中に入れる。Kafka は 4.0（2025-03-18）で ZooKeeper を廃止して KRaft だけになった。ただし Kafka のデータの複製は ISR 方式で、`acks=all` は fsync を待たない。Redpanda は過半数の fsync を待つ（本番モードの既定）[21][21a][23][24]
30. 「Raft を使っている」ことは正しさの証明ではない。Jepsen は Redpanda 21.10.1 で重複・オフセットの不整合・トランザクションの異常を見つけ、多くはその後の版で直った。版と日付のない検証結果は使わない [32]
31. マルチテナントの分離は、共有スキーマ・スキーマ分離・DB 分離・セルベースの順に、費用と運用が増え、分離が強くなる。1 つに決めず、サービスごとに混ぜる（ブリッジ）のが現実、と AWS SaaS Lens は書く。これらは任意の指針で、規範ではない [25][36]
32. セルベースは、障害とデプロイの影響を 1 セルに閉じ込める。代わりに、ルーターとコントロールプレーンが新しい共通の依存になる [26]
