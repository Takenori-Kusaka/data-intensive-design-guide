# スライドの書き手への規則

ガイド「データ指向で設計する大規模クラウドサービス ― 全体像を押さえる 9 つのステップ」の 1 Part を `deck/pNN.js` として書く。読者は新任のテックリーダー。Part の問い・結論・枚数・根拠は `research/outline.md` の表が正。焦点は `research/brief.md`。

## 1. このガイドが読者に渡すもの

本の要約ではない。大規模クラウドサービス（マイクロサービスと、共通のデータ・ETL・ログ・認証・AI・分析・セキュリティ基盤）の全体像を、柔軟性・拡張性・置換性・更新性を保って設計するための**判断の材料**と、**設計レビューで問う観点**。各 Part に次を必ず入れる。

- 判断の分かれ目（何を選ぶと何を得て何を失うか）の表
- 失敗例（公開された事後報告、またはよくある誤り）と、代わりにどうするか
- 「設計レビューで問うこと」のスライド（問い｜なぜ問うか｜危ない兆候）
- 基礎の用語は、初出で定義と図から説明する（読者は分散システムの理論を体系的に学んでいない）

## 2. Part の型

1. `L.section('Part N 題')` と `L.divider('PART N', 題, 副題, [問い 3〜4 個], ノート)`。副題に結論を先に言う
2. 問い → 用語と原則 → 判断の分かれ目 → 製品ごとの違い → 失敗例 → 推奨 → 設計レビューで問うこと → まとめ
3. 枚数は outline の値 ±2（扉を含む）。1 枚 1 メッセージ。**タイトルは結論の文**（34 字以内）

## 3. 使ってよい道具（`lib.js` のヘルパーだけ。pptxgenjs を直接呼ばない。例外は `s.addShape(SH.LINE…)` などの単純な図形）

```js
module.exports = (L) => {
  const { C, SH, HEX } = L;
  L.section('Part 6 データの流れを設計する');
  L.divider('PART 6', '題', '副題（結論）', ['問い', …], 'ノート');
  {
    const s = L.content('タイトル（結論の文）', { lead: 'リード 1 文', stages: [3], tag: 'ステップ 4', notes: '…', refs: { spec: '…', inst: '…', book: '…' } });
    L.table(s, [[見出し…], [行…]], { x: 0.6, y: 1.95, w: 12.1, colW: [..], fontSize: 11.5, rowH: 0.5 });
  }
};
```

- `L.content(title, {lead, stages, tag, notes, refs})`、`L.divider`、`L.table`、`L.card`、`L.note(s, kind, text, {x,y,w,h,size,label})`（kind：leader・warn・tip・add・decide）、`L.bullets`、`L.T`、`L.flow`、`L.box`、`L.arrow`、`L.stat`、`L.bar`、`L.code`
- 使い方の実例は、同じ道具で書かれた `jwt-claims-guide リポジトリの deck/p03.js`・`p05.js` を読む（**中身は持ち込まない**。書き方だけ見る）
- アイコンは react-icons の `Md…` 名（実在するものだけ。例：MdStorage、MdSync、MdWarning、MdFlag、MdSchema、MdHub、MdTimeline、MdSecurity、MdGavel、MdLightbulb、MdCompareArrows、MdAccountTree、MdCloud、MdLock、MdSpeed、MdBugReport、MdChecklist、MdPerson、MdGroups、MdInsights、MdHistory、MdSwapHoriz、MdDeleteForever、MdBackup、MdRule）

### 配置（単位はインチ。スライドは 13.333 × 7.5）

- 本文の領域：x 0.6〜12.7（幅 12.1）、y 1.95〜6.5（lead があるとき）。lead が無ければ y 1.4 から。**y + h は 6.5 を超えない**（6.62 から根拠の行）
- 表：`rowH × 行数 + y ≤ 6.4`。表の下に注記を置くなら、表の下端から 0.15 以上あける。**表と他の図形を重ねない**（QA で検出される）
- 文字の大きさ：本文 12.5〜14、表 10.5〜12、最小 10.5。1 枚の文字は 350 字程度まで（表を除く）。箱の中の文は箱の大きさに収まる量にする（14pt は 1 行およそ「幅 × 5 字」、行の高さ 0.3）
- `stages`：パンくずの番号。0 要件、1 所有、2 モデル、3 流れ、4 契約、5 複製、6 正しさ、7 導出、8 基盤。その Part のステップを点灯する（基礎の Part は関係するステップを 1〜2 個）
- `tag`：`'ステップ 4'`、`'基礎'`、`'考え方'` など

## 4. 根拠の行（全スライド必須）

`refs: { spec, inst, book }` のうち、当てはまるものを 1〜3 個。1 個 60 字程度まで。

- `spec`（仕様・文書）：標準、製品の公式文書（**版と確認月**）、原論文（著者・年）。例：`PostgreSQL 18 文書 26.2.8 Synchronous Replication（2026-11 確認）`
- `inst`（指針・報告）：公的機関、クラウド各社の設計指針、事業者の事後報告（事業者・発生日）、Thoughtworks Radar
- `book`（書籍）：`『データ指向アプリケーションデザイン 第2版』8.2.4 節 p.297`。書名は初出以外 `DDIA 2e`、`『ハードパーツ』`、`『大規模データ管理 第2版』`、`『プラットフォームエンジニアリング』` と略してよい。**ページは印刷ページ**。一般論として引くときは `（考え方）` を付ける
- 根拠が無い主張は、スライドに `L.note(s, 'add', …)`（ラベル「本ガイドの考え（一次資料なし）」）で明示するか、書かない

## 5. 事実の確かめ直し（書き手の責任）

調査ノート（`research/notes/`）と書籍の対応表（`research/books/notes/`、非公開）は下書きで、多くが要約ツール経由。**スライドに載せる数字・版・既定値・日付・ページは、書き手が原典で確かめる。**

- 書籍：`research/books/text/<ISBN>.txt`（`===== PDF p.N / printed p.M =====` 区切り）を Grep して、該当ページに本当にその記述があるか確かめる。印刷ページ＝PDF ページ − 18（DDIA 0180-2、ハードパーツ 0006-5）、− 26（大規模データ管理 0071-3）、− 24（プラットフォームエンジニアリング 0141-3）
- Web の一次資料：数字・既定値・日付を載せるものは URL を開いて確かめる。開けなければ載せないか、「未確認」と書く
- ノートに「未確認」「要確認」「記憶」とある事実は、確かめられたときだけ使う
- 確かめた結果を `research/reviews/verify_pNN.md` に表で残す：`スライドの題｜事実｜出典（URL か書籍ページ）｜確かめ方（本文確認／書籍本文で確認）｜結果（一致／修正した／載せるのをやめた）`

## 6. 実測と未検証の区別

- ケーススタディ（題材 A〜D）は測り終えた（2026-11-20）。実測の結果は `L.note(s, 'tip', '…（ケーススタディ Part 1）', {label: 'ケーススタディ（実測）'})` の形で示す。Part 1＝題材 A、2＝B、3＝C、4＝D
- 注記の文は 1〜2 文で、「何を、どの条件で流し、何が起きたか」。数字はケーススタディの `results/<題材>/summary.md` と `results/RERUN.md` から写す（記憶や計算で作らない）
- 実験は 2 回流してある。2 回で値が違うものは「1 回目 a・2 回目 b」と並べ、有無が変わったものは断定しない。「0 件」には試行の数を添える
- 実測は 1 台の Docker 環境・小さな規模・少ない試行のもの。ガイドの主張を実測より強くしない（「実測で証明された」「必ず」と書かない）。性能は同じ環境の中の相対比較と書き、製品の優劣を断定しない
- 一次資料で確かめられなかった点を実測したときは、「一次資料では確かめられなかったが、ケーススタディで実測した：…」と書く（「確認した」とは書かない）。測っていない点は「ケーススタディでは測っていない（未検証）」
- 実測を足したスライドの根拠の行は、`spec` か `inst` の末尾に「／ケーススタディ Part N」を足す（60 字程度を超えるなら足さない）
- 照合の行とスライドの対応は `research/reviews/reflect-casestudy.md` に残す
- クラウドのマネージド製品の表は、題か注記に「公式文書の記述（2026-11 確認）。未検証」と入れる
- 公称値（SLA、RPO・RTO）は「公称」と書く。事後報告は事業者の自己申告

## 7. 言葉

- 訳語は DDIA 2e に揃える：記録のシステム（system of record）、導出データ、逐次更新（rolling upgrade）、発展性、ロストアップデート、ライトスキュー、クォーラム、線形化可能性、チェンジデータキャプチャ（CDC）、障害（fault）と機能不全（failure）
- 『ハードパーツ』の「CDC」はコンシューマー駆動コントラクトのこと。このガイドで CDC はチェンジデータキャプチャだけを指す
- 4 つの性質：柔軟性・拡張性・置換性は JIS X 25010:2025 の Flexibility・scalability・replaceability に対応づける（Part 1 で説明済みとしてよい）。更新性は「動かしたまま、利用側を止めずに変えられること」という本ガイドの定義
- 平易な日本語。1 文は短く。用語は初出で 1 行の定義。煽らない（「必須」「絶対」「革命的」を使わない）。原典より強く言わない
- 数字には条件（何を、どの版で、いつ）を付ける。「最近」「近年」は使わず年を書く
- 本文と図の転載はしない。書籍からの引用は 25 字未満、1 Part に 2 か所まで
- 法律に関わる記述は「法務に確認」を添え、助言と読める書き方をしない
- 実在の企業の内部事情を推測で書かない。事後報告に書かれたことだけ

## 8. 発表者ノート（全スライド必須）

読むだけで発表できる量（250〜450 字）。スライドに書けなかった説明、但し書き、数字の条件、次のスライドへのつなぎ。「です・ます」体。

## 9. ほかの Part との関係

- ほかの Part が扱う話は「（Part 9）」のように参照だけ書き、重ねて説明しない。outline の表で担当を確かめる
- 架空のサービスの例が要るときは、ケーススタディと同じ「架空の宅配注文サービス（注文・在庫・決済・通知）」を使う

## 10. 確認

```bash
cd deck
export NODE_PATH="<pptxgenjs などを入れた node_modules のパス>"
node build_one.js pNN      # qa/pNN.pptx ができ、枚数・refs 漏れ・ノート漏れ・長い題が出る
```

エラーなく組み立てられ、`without refs: 0 without notes: 0`、長い題の警告なし、になるまで直す。PowerPoint での見た目の検査（はみ出し・重なり）は取りまとめ役が行うので、**PowerPoint は起動しない**。書くファイルは `deck/pNN.js` と `research/reviews/verify_pNN.md` だけ。
